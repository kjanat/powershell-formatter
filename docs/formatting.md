# Formatting behavior and PSScriptAnalyzer compatibility

The default configuration reproduces PSScriptAnalyzer's `CodeFormatting`
preset. Parity is enforced by [`tests/pssa-parity`](../tests/pssa-parity): fixtures are generated by
running real `Invoke-Formatter` (module version pinned in
[`tests/pssa-parity/expected/VERSION`](../tests/pssa-parity/expected/VERSION)) over the inputs under several
profiles, and the Rust formatter must match byte-for-byte *and* treat the
oracle's output as a fixed point.

## Rule mapping

| PSSA rule                  | Options                                                                                                                                                                                                                      |
| -------------------------- | ---------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| PSPlaceOpenBrace           | `placeOpenBrace`, `braceStyle`, `newlineAfterOpenBrace`, `ignoreOneLineBlock`                                                                                                                                                |
| PSPlaceCloseBrace          | `placeCloseBrace`, `branchKeywordPlacement`, `noEmptyLineBeforeCloseBrace`, `ignoreOneLineBlock`                                                                                                                             |
| PSUseConsistentWhitespace  | `spaceBeforeOpenBrace`, `spaceInsideBrace`, `spaceAfterKeyword`, `spaceAroundOperator`, `spaceAfterSeparator`, `spaceAroundPipe`, `collapseSpaceAroundPipe`, `collapseSpaceBetweenParameters`, `ignoreAssignmentInHashtable` |
| PSUseConsistentIndentation | `indentation`, `indentWidth`, `useTabs`, `pipelineIndentation`                                                                                                                                                               |
| PSAlignAssignmentStatement | `alignAssignment`                                                                                                                                                                                                            |
| PSUseCorrectCasing         | `keywordCasing`, `operatorCasing`, `commandCasing` (+ injected catalog)                                                                                                                                                      |

Presets: `FormatOptions::default()` = CodeFormatting/Stroustrup,
`::otbs()`, `::allman()`.

## Empirically verified PSSA semantics we reproduce

These were discovered by probing `Invoke-Formatter` 1.25.0 directly (the
shipped module differs from current `master` sources in several places):

- Every brace-placement behavior applies only to **statement braces**
  (keyword construct bodies, function/class/enum bodies, switch clauses)
  plus, for the close-brace rule, multi-line hashtable braces. Script
  blocks used as expressions (`$x = {`, hashtable values) or command
  arguments (`% { }`, `.foreach({`) are never moved — in same-line *and*
  next-line mode.
- Whitespace normalization around operators covers assignment operators,
  `+ - * / %`, **every** binary dash-word operator (`-eq`, `-and`, `-band`,
  `-shl`, `-f`, binary and unary `-join`/`-split`, ...), `&&`, `||` — but
  never `..`, `-not`/`-bnot`, `!`, `++`/`--`, member access, or
  redirections. A line-*leading* operator in this set is pulled onto the
  previous line.
- `CheckInnerBrace` adds a space before `}` of a one-line hashtable but not
  after `@{` (only `LCurly` tokens are checked on the open side).
- In multi-line hashtables, `=` spacing is left to the alignment rule: the
  gap *before* `=` is aligned, the text after `=` is untouched (so `a  =1`
  is canonical PSSA output).
- Every indentation opener (`{ @{ ( @( $(`) increments the level — so
  `.foreach({` bodies sit two levels deep — except a `(` that starts a line
  and has content after it on the same line. `[` never affects indentation.
- Pipeline indentation restores at the end of the **outermost** pipeline;
  increments from pipelines nested inside another pipeline's script blocks
  accumulate outward (see [pssa-quirks.md](pssa-quirks.md) for why).
- Corrections anchored on opening tokens push existing trailing spaces onto
  the next line (where reindentation eats them); corrections anchored on
  closing tokens leave the spaces in place, producing PSSA's characteristic
  trailing whitespace after one-line-block expansion. We reproduce both.

## Intentional divergences

Documented differences from `Invoke-Formatter`, all deliberate:

1. **`--%` pipe spacing.** PSSA inserts one more space before a `|` that
   terminates a `--%` verbatim argument on *every* run — it is not
   idempotent (verified; see pssa-quirks.md). We never touch spacing
   adjacent to a verbatim argument.
2. **Range formatting coordinate drift.** PSSA filters corrections against
   the requested range per fix iteration while earlier fixes shift text, so
   trailing corrections silently drop out of a range. We apply exactly the
   corrections whose *original* span lies inside the range — stable and
   editor-friendly.
3. **Mixed newlines.** PSSA throws on input with mixed line endings. We
   normalize the newlines we own to the first style used between tokens
   (newlines inside strings are never touched) — and `endOfLine` can force
   `lf`/`crlf`.
4. **Width-aware pipeline reflow.** Beyond PSSA: lines longer than
   `lineWidth` that contain pipes are broken after each pipe (then indented
   per `pipelineIndentation`). Only ever adds breaks, never joins; disabled
   with `lineWidth: 0`. PSSA never re-flows lines.
5. **Malformed input.** PSSA formats whatever parses partially;
   we refuse to touch structurally uncertain input (unbalanced/unterminated
   syntax) and return it unchanged with diagnostics — an editor buffer
   mid-keystroke is never corrupted.
6. **Alignment with comments between key and `=`.** PSSA widens the
   left-hand side by the comment text; we leave such entries unaligned
   (their width still shapes the group). This avoids reordering comment and
   alignment padding.
7. **Nesting depth.** PowerShell's own parser refuses scripts nested
   deeper than roughly 10k–20k levels (`ScriptTooComplicated`); we parse
   and format at least 32 000 levels on a 1 MiB stack — depth costs heap,
   not call stack — with a 131 072-level sanity cap that declines the
   usual way (input preserved, diagnostic emitted). Beyond pwsh's ceiling
   there is no oracle to compare against, so those inputs are covered by
   our own invariant tests — losslessness, idempotence, preservation —
   rather than parity fixtures.

## Command and parameter casing

PSSA queries a live runspace via `Get-Command`. This formatter accepts an
injected `CommandCatalog` (JSON: `{ "commands": { "Get-ChildItem":
["Path", ...] } }`). Without a catalog, keyword/operator casing still work
and output is deterministic; unknown commands are always left as written
(matching PSSA's behavior for unresolvable commands). The parity suite
generates its catalog from the same pwsh session that produced the
fixtures, so the catalog path is oracle-tested.
